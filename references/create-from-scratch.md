# 从零构建PPT的教程

## 制定任务计划

> **任务命名约束（强约束）**：本表仅为内部执行参考。在创建 TODO / 任务清单或向用户汇报进度时，**必须使用面向用户的术语**（如「内容大纲 / 风格设计 / 创建演示文稿 / 逐页制作 / 检查页面 / 交付」），**禁止暴露任何内部实现字眼**（如 `JSX`、`DSL`、`*.jsx`、`OOXML`、`success=true`、源码、组件文件名等）。

| Step | 职责（内部）                                   | 产物（内部）                                 |
| ---- | ---------------------------------------------- | -------------------------------------------- |
| 1    | 信息收集（数据/时效类主题硬性前置）         | 背景资料 / 行业数据                          |
| 2    | 需求对齐（轻量确认 + 风格预览卡）              | 关键信息已确认 + 风格参数已锁定              |
| 3    | 依据主题+信息构建PPT的叙述逻辑                 | `STORY.md`                                   |
| 4    | 构建页面风格的设计逻辑                         | `DESIGN.md`                                  |
| 5    | 空编译确认引擎可用（`node src/cli.mjs validate <项目>/slides`） | 引擎就绪                                   |
| 6    | 逐页生成 PPT（按大纲顺序写完全部页面）         | 全部页面已生成                               |
| 7    | 校验并修复页面                                 | 全部页面校验通过                             |


## 各步骤要求
### Step1：信息收集（数据/时效类主题的硬性前置，非可选）

> 把「信息收集」从软提示升级为**可验收的硬流程**。目的：数据深度/广度不靠模型临场发挥，靠硬性数量指标兑底。

**触发判断**：主题涉及 `数字 / 市场 / 行业 / 新闻 / 竞品 / 分析 / 战略` 等时效或数据敏感内容时，**必须执行本步**，不达标禁止进入 Step3。

**Step 1a：生成搜索查询（8–12 条，并行）**

按以下 5 层覆盖式生成查询，**禁止只搜其中一层**：

| 层 | 查询模式 | 示例（竞品分析） |
|---|---|---|
| Foundation 定义 | `[主题] 定义/概述` | 扫地机器人 行业概述 |
| Context 背景 | `[主题] 历史/发展` | 扫地机器人 发展历程 |
| Evidence 证据 | `[主题] 统计/数据/份额 [年份]` | 扫地机器人 市场份额 2025 |
| Application 应用 | `[主题] 案例/打法/对标` | 石头 追觅 科沃斯 竞争打法 |
| Trends 趋势 | `[主题] 趋势/未来/预测` | 扫地机器人 2026 技术趋势 |

> 时效性主题必须带上年份（当前年份）；中英文混合查询。**竞品/战略类额外加一层「财务/营收」查询**（如「石头科技 营收 2025 财报」），否则竞品分析会缺真实财务数据。

**Step 1b：组织成 6 维度**

搜到的材料强制归类到 6 维度，缺一维即视为收集不完整：

1. Overview 概述（定义、意义）
2. Background 背景（历史、里程碑、现状）
3. Key Info 关键信息（事实、数据、权威观点）
4. Evidence 证据（案例、研究、对标数据）
5. Analysis 分析（多角度、对比）
6. Outlook 展望（趋势、建议）

**Step 1c：质量验收（硬门槛，不达标→继续搜）**

- 优先学术/官方/一手来源；排除未验证或过时（>5 年）内容；
- **≥3 个高权威来源**（官方报告/IDC/奥维云网/上市公司财报等）；
- **≥5 个不同域名**；
- 竞品/战略类：竞品必须附**真实财务数据**（营收/增速/份额），不能只有百分比排名。

若用户已提供完整参考材料（长文本、`.docx`、`.pdf` 等），本步降级为「只查陌生概念 + 用联网搜索补材料缺失的行业背景」，不做 5 层全搜。

### Step2：需求对齐
**必读 [human-alignment.md](references/human-alignment.md) 全文并按其执行（本步唯一权威，冲突以它为准）**。要点：
- 先按 human-alignment.md §2.2 逐项判断缺失（P0 主题 / P0.5 分析主体 / P1 目标 / P2 场景 / P3 受众 / P4 忠实度），再决定问什么
- **拷打判断（human-alignment.md §2.3 触发条件）是硬性门禁**：命中必问条件（分析主体缺失 / 主题有歧义 / 首轮答案仍模糊）时**必须追问**，禁止用「能推断就推断」跳过——本条与 Step 其它表述冲突时以 human-alignment.md 为准
- 文字提问**一次问完**（≤3 题）：有结构化提问能力（如 `clarify`）就一次调用发全部题目；没有就在一条回复里列成编号问题。风格选择默认也一并问（4 个风格选项），满足 human-alignment.md §2.3 跳过条件时可省略。
- **问完必须结束回合等用户回答**，不得自问自答或假定答案继续。
- 无论是否提问，进入 Step3 前必须确保：主题明确、受众可定位、风格参数已确定（用户选定或 AI 推导并在 DESIGN.md 记录依据）
- 对齐结果中的主题/目标 → 作为 Step3 构建叙事的输入
- 对齐结果中的风格参数（色板/字体/密度基线）→ 作为 Step4 设计阶段的硬约束

### Step3：构建叙事逻辑 （STORY.md）
阅读 [story-principle.md](story-principle.md)，最后生成一个STORY.md的文件。

### Step4：构建页面风格的逻辑 (DESIGN.md)

#### 风格匹配流程

收到用户需求后，执行以下推理判断是否命中预设风格：

**第一步：提取用户意图特征**
从用户 query 中识别：主题领域、目标受众、使用场合、调性倾向。

**第二步：与预设风格比对**

| 风格 | 核心调性 | 适用场景 |
| :--- | :--- | :--- |
| [学术风](references/designs/design-principle.academic.md) | 可信、证据驱动、蓝白克制 | 高校答辩、科研结题、教学课件（理工医）、学术会议、学科评估、临床/医学汇报、课题开题、实验室组会、科研申报 |
| [商务咨询](references/designs/design-principle.consulting.md) | 权威、数据密集、结构化分析 | 战略/行业研究、高管 review/董事会、投行/IPO 路演、咨询交付物、企业转型/组织变革、私募/风投/行研、尽职调查 |
| [红金政务风](references/designs/design-principle.redgold.md) | 庄重、红金热烈、中文优先 | 党政机关汇报、政务/公共部门、国企央企汇报、党课/学习宣讲、周年庆典/红色文化、表彰大会、纪检巡察 |

**第三步：做出判断**

判断标准：用户的场景是否**明确属于**上表某风格所服务的特定领域和受众。

- **命中**：用户场景明确落在某风格的适用场景内 → 使用该预设风格；
- **不命中**（默认路线）：用户场景不属于上述三类特定领域，或场景模糊/泛化/跨领域 → 走通用设计原则；

> ⚠️ **重要原则**：预设风格是为特定垂直领域定制的，不应泛化使用。大量常见场景（如：产品介绍、项目提案、工作总结、培训课件、技术分享、营销方案、团队介绍、述职报告、年终总结等）都应走通用设计原则，由 AI 根据具体需求自由设计。只有当用户场景**明确且典型地**属于学术科研、专业咨询、或党政红色这三个垂直领域时，才使用预设风格。

**判断示例**：
- "做一个硕士毕业答辩PPT" → 明确属于学术场景 → 命中学术风 ✅
- "做一个麦肯锡风格的行业分析" → 明确属于咨询场景 → 命中商务咨询 ✅
- "做一个党支部年度工作汇报" → 明确属于党政场景 → 命中红金政务风 ✅
- "帮我做个述职报告" → 职场通用场景，不属于上述三类特定领域 → 走通用 ✅
- "做一个产品发布会PPT" → 产品/营销场景 → 走通用 ✅
- "做一个季度工作总结" → 职场通用场景 → 走通用 ✅
- "做一个AI技术分享" → 技术/科普场景 → 走通用 ✅

#### 匹配后的执行

- **命中预设风格**：读取对应风格文件，结合用户实际需求设计PPT，**禁止额外生成DESIGN.md**，可以显式声明哪些颜色、字体等内容需要结合用户需求微调；
- **不命中（默认路线）**：读取通用[设计原则](references/design-principle.md)，结合用户实际需求生成DESIGN.md；


### Step5：编译与逐页视觉验收准备
> **本步是硬约束**：进入逐页生成前，先跑一次空编译确认引擎可用。slides-engine 是**离线一次性编译**（无实时编译服务、无实时预览面板），编译命令如下：
>
> ```bash
> cd slides-engine            # 进入本 skill 目录
> node src/cli.mjs validate <项目目录>/slides   # 机器校验（先建 slides/ 目录，空目录也会通过）
> ```
>
> **文件名命名约束**：`.pptx` 文件名默认使用中文（如 `"季度汇报.pptx"`、`"项目提案.pptx"`），只有用户明确要求英文文件名时才用英文。
>
> **逐页视觉验收替代实时预览**：slides-engine 没有实时预览面板。等价能力是 `render-png` 子命令——每写完一页，立即用 `node src/cli.mjs render-png <该页.slide> --out <该页.png>` 导出该页 PNG，交给视觉模型对照 DESIGN.md 契约检查。这就是"逐页即时自检"的引擎支撑（详见 SKILL.md 约束 B）。


### Step5.5：模板选型（强制，每页先选模板再填空）

> **机制**：不采用「从空白画布发明版式」的做法——而按 `页面类型 → 内容结构 9 类型 → 3 优先级匹配` 从模板库选出页面级成品模板，再替换占位文字。模板已内置完整布局/装饰/页脚，Agent 只填内容，天然全篇一致、不产生版式类返工（页脚漂移/等宽卡/无锚点等）。**逐页生成前，每页必须先完成模板选型，命中就用模板填空；仅模板库无匹配时才允许手写，且手写页必须过全部动笔自检。**

逐页执行（在写每一页 .slide 前，先完成本页选型）：

1. 读 `references/templates/template-library.md`（索引 + 匹配规则）。
2. 判本页页面类型：cover / toc / transition / ending / content（content 再判「内容结构 9 类型」：argument/data/process/case/comparison/concept/problem/trend/summary）。
3. 按 3 优先级匹配选模板：
   - **优先级 1 布局结构**：有图 → 含 Image 模板；无图 → 纯结构图/卡片模板；数据冲击 → data；流程/阶段/架构 → process（禁卡片横排）。
   - **优先级 2 内容密度**：1-2 点 → 大留白居中；3-4 点 → 标准两栏/卡片；5+ 点 → 密集网格。
   - **优先级 3 视觉多样性（强制）**：同一 content 模板全篇 ≤ 2 次、相邻页不得同模板；非对称版式 ≥40% 沿用。
4. 风格定位：封面/转场/结尾先按整篇基调定风格（business/tech/black-gold/chinese/…→ 编译 theme 映射），内容页在对应风格子目录挑；**命中预设风格分支（academic/consulting/redgold）时，选对应主题模板并叠加分支色板**（black-gold→redgold 主题等）。
5. 读选中的模板 .slide → 替换 `{{替换：xxx}}` 占位 → 按需增删条目 → 写为 `slides/{NN}.slide` → validate。
6. 记到本页 DESIGN.md 映射表 `关键约束` 列（如「模板 content/business/1531」），保证逐页可溯。

> 模板库缺某类型/风格（如政务党建 redgold 无专用模板）时，**最小变通**：选结构最接近的模板（如 black-gold→redgold）改色板/字体到分支常量，或手写页——手写页必须完整满足 Step6 动笔自检 10 条 + SKILL.md 约束 B/C，并复用已验过的页脚/底条写法（满高根容器内 absolute bottom:20 锚画布底，见 design-principle 页脚细则）。

### Step6：逐页生成 PPT（按大纲顺序）
> 动笔前的心智校准：每一页是一个 `.slide` 文件，但**它不是 React**——这是一套受限 DSL，工程直接编译成 OOXML（.pptx）。把它当 HTML + 内联 CSS 来写。禁止引入 React 生态任何概念（`import` / `export` / `module` / hooks / state / 函数组件定义），文件最后一个表达式必须是 `<Slide>`。
>
> 动笔前必读：
> - `STORY.md` - 当前PPT的叙事逻辑
> - `DESIGN.md` — 当前 PPT 的设计稿（画布、配色、字号、布局、元素、密度）
> - 相关组件规范 — 本页用到哪个组件，就读取 `references/component-*.md` 中对应文档
>
> **动笔前禁读**：本项目目录之外的任何 PPT 项目源码（详见 §Step 5 设计依据封闭原则）。本页 JSX 的全部依据应来自 `DESIGN.md` + 命中分支 `design-principle.<id>.md` + `component-*.md`，不得"借鉴"历史项目的 jsx 写法或视觉选择。
>
> 严禁仅靠记忆动笔。

约束如下：
- 充分结合 `STORY.md` 和 `DESIGN.md`，按照大纲顺序从第 1 页生成到第 N 页，一次写完全部页面；
- 配图前置：若涉及到生图内容，必须在写内容前完成生图流程，**并且对生成的图片进行视觉检查，确认图片清晰、无水印且符合上下文后方可使用**；
- 写入页面源文件：用你环境的写文件工具写到 slides/{NN}.slide；
- 动笔自检（每页提交前 10 条硬约束，逐项确认；任意不通过 → 当页返工） 
  - 母版区齐全：默认三区（A 标题块 0–120px / B 内容区 120–660px / C 页脚条 660–720px 含右下页码 NN/TOTAL）； 
  - 标题块右侧不得塞装饰小图（200×70 这种），全篇位置严格一致； 
  - 本页 L1 主视觉占 B 区面积 ≥ DESIGN.md 规定（默认 30%）；不得用 L3 角标顶替 L1 
  - 仅使用项目 DESIGN.md 列出的 ≤ 4 种 hex 与 ≤ 2 套字体家族 
  - 与上一页版式不重复；本页留白比例 ≤ DESIGN.md 上限（常规页 ≤ 35%） 
  - 本页有 ≥ 1 个视觉锚点（≥ 44px 元素 或 ≥ 40% B 区面积的图）；如无 → 必须补充巨型数字/大图/大色块 
  - 本页与上一页视觉重量有显著差异（最大元素面积比 > 1.5:1 或版式结构明显不同）；连续 ≥ 2 页等宽卡片横排 → 返工 
  - 本页色彩分配符合 DESIGN.md 页面映射表：强调色只出现在焦点元素上，主色/辅色/强调色面积比合规 
  - 本页的 role 与 STORY.md 一致：hero 页必须有 ≥ 40% B 区主视觉或 ≥ 48px 锚点数字；supporting 页不得使用 hero 级视觉投入


### Step7：页面校验与修复
所有页面写完后，一次性跑全量校验。如果返回内容中包含`success: false`, 请根据工具的返回结果去修复有问题的页面。
最终必须要确保所有页面语法正确。

```bash
node src/cli.mjs validate <项目目录>/slides --theme <theme>
```
